# Refreshing embedded Stage 2 device trees

The U-Boot payload route selects a DTB appended to Aura. Linux receives that
selected tree, including firmware fixups, through U-Boot/EFI. Installing an
Image, modules or a DTB under `/boot/dtb` does not refresh the embedded set.
For example, a kernel with the PMP DRAM reporting driver can bind successfully
but expose no `dram/` group if the selected boot DT predates the DRAM properties.
The kernel must continue to treat absent DT data as unsupported.

Recompose the Stage 2 payload whenever its kernel DT source changes. Use the
DTBs generated by the intended kernel checkout, rather than extracting and
reusing the DTBs in the installed Stage 2. Keep board selection and firmware
profiles in the DTs; the composer does not select a SoC or invent properties.

Build the DTBs from the pinned, clean kernel checkout (including any separately
reviewed boot compatibility prerequisites):

```sh
kernel_commit=$(git -C "$kernel" rev-parse HEAD)
make -C "$kernel" O="$kernel_out" ARCH=arm64 LLVM=1 defconfig
make -C "$kernel" O="$kernel_out" ARCH=arm64 LLVM=1 dtbs
```

Build a bare Aura with `RELEASE=1 CHAINLOADING=1 ESP_STAGE2=1
BUILTIN_LOGO=aurora`, and use a separately qualified `u-boot-nodtb.bin`.
Compose one or more freshly generated board DTBs explicitly:

```sh
python3 tools/compose_stage2.py \
  --aura aura-stage2.bin \
  --kernel-commit "$kernel_commit" \
  --dtb "$kernel_out/arch/arm64/boot/dts/apple/t6040-j616s.dtb" \
  --dtb "$kernel_out/arch/arm64/boot/dts/apple/t8140-j700.dtb" \
  --uboot u-boot-nodtb.bin \
  --output stage2-new.bin
```

The output is Aura + DTBs + deterministic gzip U-Boot. Its adjacent JSON receipt
records the kernel revision and each component's name, offset, size and SHA-256.
The tool checks the DTB headers and requires a bare Stage 2 input, preventing an
old appended DTB set from being carried forward accidentally. The supplied
kernel revision is a provenance declaration: the caller must verify that the
DTBs came from that checkout and preserve its build log and configuration.

If the installed payload has configuration lines after U-Boot, preserve the
required lines in a local file and pass `--variables variables.txt`. Lines must
be newline terminated; do not append a NUL terminator. Stage 1 appends its own
handoff configuration and terminator in RAM. Machine-specific variables and
images remain local and must not be committed or included in a public report.

Before deployment, compare the embedded DT with the candidate DT, review all
static differences, and confirm the required properties in the candidate.
For DRAM reporting these are the PMP report node's `apple,dram-type`,
`apple,data-bus-width`, `apple,dcs-state-count`,
`apple,peak-bandwidth-bytes-per-second`,
`apple,bandwidth-class-bytes-per-second`, and `operating-points-v2`, plus the
referenced DRAM OPP table containing `apple,data-rate`.

The lead deploys the reviewed payload to the Stage 2 path selected by Stage 1
(for example `aurora/stage2.bin` on the ESP), retaining the current image and
its hash for rollback. Use the existing approved one-shot/bootguard process;
composition performs no installation, boot-default change or reboot. After
boot, inspect the live `/sys/firmware/fdt` and PMP `dram/` files to verify the
selected tree, rather than inferring success from installed DTB files.

The direct `boot=` route described in the J700 installation guide instead
loads the DTB named in the four-field boot specification. Refresh that named
file together with its kernel and modules; it is a different packaging route.
